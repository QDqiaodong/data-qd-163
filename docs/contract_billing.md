## 共享设施预约结账 v1 (`calendar-billing`)

`calendar-billing` 是第七个、增量式入口；前六个命令的接口与语义完全不变。它在一个本地
SQLite 文件中维护一本共享设施的**预约结账账簿**：运营方用 `replace` 整体替换当前认可的
预约清单，财务用 `close` 按服务月顺序出账，`show` 只读查询已关账月。`init` 是唯一能创建
账簿的动作。

命令固定为 `calendar-billing --db DB --source INPUT`，没有 `--output`；成功时只向 stdout
打印一个 JSON 对象（不带 `schema_version`/`source_sha256` 外壳，直接是本操作的 `result`）。

### 账簿配置（`init`）

根对象恰含 `action`、`timezone`、`first_month`、`rooms`。

* `timezone` 是账簿固定的 IANA 结账时区，初始化后不变；系统必须提供该时区。
* `first_month` 是最早可出账的服务月，格式有效 `YYYY-MM`，年份 0002..9998。
* `rooms` 为 1..32 项，每项恰含 `room`（标识符，全局唯一）、`free_minutes`
  （0..1000000 整数）、`unit_cents`（1..1000000 整数分，每超额分钟价格）。
* 一间房在每个服务月各有一份免费额度，不结转；同一房不同月重新计算。
* `init` 只创建尚不存在的账簿：目标文件已存在（含符号链接、空文件）即失败，旧账簿永不
  被覆盖。成功返回 `{"first_month": <first_month>}`。

### 预约清单（`replace`）

根对象恰含 `action`、`bookings`。每项恰含 `room`、`account`、`rule`：

* `room` 必须是已配置房间；`account` 是成本中心标识符；`rule` 是现有完整重复日历规则
  （与 `calendar-expand` 相同的字段、边界与 gap/fold 语义）。
* `schedule` 在本次清单中唯一。至多 128 条规则、展开后至多 16384 个实例；同一实例
  （同一 `schedule` 的同一 `nominal_date`）只按一次预约计费。
* 清单是**全部当前认可的预约**，含仍有效的往期与未来预约。遗漏的历史预约表示撤回它。
  空清单合法。`room`、`account`、`rule` 都可在替换时修订。
* `replace` 整体替换成功返回 `{"occurrence_count": <展开实例数>}`；任何规则非法、
  `schedule` 重复、房间未知、实例超限或服务月越界都使整次替换失败且不留部分更新。
* 全部规则（含展开为空的规则与非法尾项）都先完整校验，不受任何计数或结论短路影响。

按原规则展开，保留未做 gap/fold 解析时的名义日期 `nominal_date`。每个生成实例只归一个
服务月：把真实 UTC 起点转换到结账时区，取当地年月。哪怕跨月也把整段 elapsed 分钟归给
起点所在月。服务月落在 `first_month` 至 `9998-12` 之外的实例使整次 `replace` 失败。

### 免费额度消耗与计费

每个 `(服务月, 房间)` 内按真实 UTC 起点从早到晚消耗免费额度；同一时刻按
`(schedule, nominal_date)` 的 Unicode 码点顺序决定先后。每个实例独立消耗自己的整段时长，
即使区间重叠也不取并集；实例可部分免费，只对超出剩余额度的分钟按单价收费。真实起点保留
秒级精度（历史秒级偏移，如巴黎 1900 年的 `08:50:39Z`），不能按本地墙钟顺序或截断到分钟
排序，因此回拨时两个墙钟表面相同的实例仍按真实 UTC 早晚决定谁先用额度。

### 关账（`close`）与查询（`show`）

两者都恰含 `action`、`month`；`month` 是有效 `YYYY-MM`（年份 0002..9998）。

* 第一次 `close` 只能关闭 `first_month`，其后每次新关账只能关闭上次之后紧邻的一个月。
  跳月失败；没有本月预约也可关账。不从系统时钟推导账期。
* 对任何已关账月重试 `close`，返回**原账单**，不消耗、也不重算待入账的补差。
* `show` 只读，返回指定已关账月的同一份账单；未关账月报错。

### 账单结构

账单为 `{month, charges, adjustments, account_totals}`：

* `charges` 是本服务月当前每个预约实例的初次计费，免费实例也列出。每行含身份五字段
  `service_month, room, account, schedule, nominal_date` 与整数 `amount_cents`，另含
  `start_utc`（`YYYY-MM-DDTHH:MM:SSZ`）、`minutes`、`free_minutes`。
* `adjustments` 是所有更早服务月需要在本月入账的补差。每个发生过变化的
  `(服务月, 房间)` 先以当前清单还原该服务月应有的逐行费用，再与**该行累计已经入账的
  金额**比较；只列金额非零的差额。正数是补收，负数是冲回。
* `account_totals` 是按 `account` 排序的 `{account, amount_cents}` 数组，只列本账单至少
  有一行明细的成本中心，金额是该中心在两类明细中的代数和，允许为零或负数。

两个明细数组分别按五元身份（`service_month, room, account, schedule,
nominal_date`）的码点顺序排序。

#### 行身份与累计入账

行身份是 `(service_month, room, account, schedule, nominal_date)`。旧行若在当前清单中
消失，应收按零算（即冲回该行累计已入账金额）；新行以往未入账则已入账金额为零。**已入账
金额包含原账单和之后实际开出的所有补差**，不是只拿原账单比较。因此历史实例更换房间、
成本中心或服务月时，会冲回旧行已入账的收费（旧行应收变零），同时为新行计费，绝不把旧
费用整笔改挂到新行。应补给同一个成本中心的正负明细也不能互相抵消后省略。

首次关账对外产生账单、固定归档以及确认这些补差已入账是同一次成功操作：`close` 在一个
`BEGIN IMMEDIATE` 事务中完成该月的入账与 `posted` 累计投影的更新，失败整体回滚。后续改过
预约并开出新账单后，`show` 与重复 `close` 仍返回原来的明细与汇总。

#### 累计入账投影的正确性

账簿持久保存一张 `posted` 投影，键为行身份、值为“迄今累计已入账金额”（原账单 + 所有已
实际开出的补差）。每次 `close` 对每个早于本月的服务月：

1. 以当前清单重算该服务月应有的逐行金额；
2. 对当前有、`posted` 有或无的行，差额 = 应收 − 已入账（无则 0）；
3. 对当前已消失而 `posted` 仍有的行，差额 = 0 − 已入账（即全额冲回）；
4. 只把非零差额写入本月 `adjustments`，然后把该月 `posted` 重置为当前应收。

这样无论历史开过多少张补差账单，比较的基准都等于账簿上真实开出的合计，而不会因为多次
重算原账单而漂移。

### 数据库文件规则

* 只由合法 `init` 创建不存在的数据库；其他动作对不存在、非本功能（按表名识别）或非
  SQLite 文件报错，且不清空或覆盖已有内容。不提供旧库迁移。
* `DB` 不得是符号链接；解析后的 `DB` 与 `INPUT` 路径必须不同。
* 每次成功的 `replace`/`close` 是同一个 `BEGIN IMMEDIATE` 事务；`show` 在一致读事务中
  只读、不写、不取写锁。WAL 允许一个写者与读者并发，写者之间由 SQLite 写锁串行。
* 被拒绝的首次 `init` 不留下数据库或 `-wal`/`-shm` 文件。

### 持久投影

账簿持久保存以下表，供跨进程读取与审计：

* `meta` 存固定配置 `timezone`、`first_month`；
* `rooms` 存每间房的 `free_minutes`、`unit_cents`（初始化后不变）；
* `bookings` 存最近一次 `replace` 的每条规则（`rule_json` 为审计副本，计费不读它，
  只读 `instances`）；
* `instances` 物化最近一次 `replace` 展开的每个实存实例及其服务月、房间、成本中心、
  名义日期、真实起点与分钟数；
* `bills` 按服务月保存已归档账单的 `charges`/`adjustments`/`account_totals` 三份 JSON，
  `show` 与重复 `close` 都从这里原样读出；
* `posted` 按行身份保存累计已入账金额（仅非零行），是补差比较的持久基准。

正确性义务：`replace` 在一个事务里同时替换 `bookings` 与 `instances`，使规则快照与实例
永远描述同一次清单；`close` 在一个事务里同时重算全部更早服务月的差额、重置这些月的
`posted`、为本月入账并写入 `bills`，故原账单、补差与累计投影不会被观察到互相矛盾。


### 严格 JSON 与错误

标识符沿用 `common.ident`（非空、无首尾空白、≤128 字符、无控制字符），并要求是有效
Unicode 标量序列、可正常编码为 UTF-8。整数位置拒绝 JSON 布尔。沿用 `common.read` 的
8 MB 上限、重复 JSON 键拒绝与非有限数值拒绝。任何非法输入、非账簿文件或操作失败退出 2，
错误只写 stderr，不输出成功 JSON，现有账簿逻辑状态不变。正常成功退出 0。

### 手算联动样例

账簿从 `2025-01` 开始，结账时区 `UTC`，房间 `R` 每月免费 60 分钟、超出每分钟 2 分。

1. 清单为 A、B 同房各 60 分钟，A 比 B 先开始，分别属甲、乙。关闭 1 月：A 收 0，B 收
   `120`。
2. 撤掉 A，补入第三成本中心丙的历史预约 C（同房 60 分钟，开始晚于未改动的 B）。重试
   关闭 1 月仍看到原账单。
3. 新关账 2 月：1 月补差为 B 的 `-120` 与 C 的 `+120`，不能因该房合计未变而省略。
4. 若清单不再变化，3 月不得重复列这两笔。
5. 另一分支：在 3 月关账前把清单改回原样。3 月反向补收 B（`+120`）并冲回 C（`-120`），
   而 1、2 月原账单仍原样可查。

可重放输入见 [fixtures/billing](fixtures/billing/README.md)，演示脚本为
`examples/demo_billing.py`。
